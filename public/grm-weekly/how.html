How this audit is made — and how it improves

The weekly grievance-redress audit is produced by a scheduled agent running against the watchlist and rules on this page. The configuration is versioned, published in full, and changes only through a logged decision (see the changelog below). Config version 1.1, updated 2026-10-03.

The pipeline

  1. Watchlist. Search the agencies below on X, over the past 7 days, using the patterns in grm-detection.json (mentions of the agency handle and replies from it, date-filtered).
  2. Classify. Keep passenger grievances about a specific service failure. Exclude praise, feature requests and official announcements — the full include/exclude rules are published with the config.
  3. Dedupe. One incident = one complaint, however many posts; follow-ups merge into the original.
  4. Replies. Detect any visible reply from the agency handle. A reply may be just a forward or a docket number — acknowledged is explicitly not resolved, and each report says which.
  5. Measure. Response rate, category counts, approximate response times decoded from post IDs.
  6. Publish. Report goes live here, to the archive index, and a summary to Telegram the same morning.
  7. Review & improve. After every run the agent reviews what it may have missed; watchlist or rule changes land as a new config version with a changelog entry, and the labeled eval set below is re-checked.

What counts, what doesn't

Included
  • passenger grievances about a specific service failure: delay, crowding, route/frequency gaps, fare or ticketing problems, staff conduct, safety/accessibility, cleanliness, breakdowns
  • threads where the rider tags the agency handle (current or legacy) — merge follow-ups into the original incident
Excluded
  • praise, thanks and appreciation posts
  • feature requests and app suggestions
  • official announcements and scheduler data posted by the agency
  • national transit stories that do not name a specific failure at the agency
  • observations that do not establish a specific failure (e.g. 'conductors prefer direct payment' with no incident)
Categories: delay, crowding, route/frequency, fare/ticketing, staff conduct, safety/accessibility, cleanliness, breakdown/maintenance, other.

Known limits

X-visible sample only — DMs, deleted posts and encrypted conversations are invisible. An agency reply means any visible response, including a generic forward or docket; it does not imply resolution. Response intervals are approximate, decoded from post IDs. This is not a count of all complaints the agencies receive.

The self-improvement loop

Detection improves through three published artifacts, all in the repo's detection/ folder:

  • Config — grm-detection.json: the watchlist, search patterns, include/exclude and reply rules the agent actually executes.
  • Changelog — CHANGELOG.md: every config change with the lesson that triggered it.
  • Eval set — eval-set.json: 13 labeled complaint posts (5 with known agency replies) plus 3 known-miss drills, seeded from past audits. After any config change, these must still be detected correctly before the change ships.

Detection changelog

Every change to grm-detection.json lands here first: what changed, the lesson that triggered it, and the eval-set outcome after the change.

v1.1 — 2026-10-03 · stale-handle repair

Lesson. The first audits under-counted Chennai and read Kerala as silent. Four of the ten watchlist handles were stale: @mtc_chennai → @MtcChennai, @cmrlchennai → @cmrlofficial, @dtc_india → @dtchq_delhi, and @KSRTC_Kerala was never the Kerala agency at all (it is @keralasrtc). A week of "no complaints found" was really a dead watch.

Change. Corrected all four handles; added handle_history so searches also cover legacy names riders still tag; added the zero_complaint_check rule — a zero week for a known-active agency triggers a handle-liveness check before it can be reported.

Eval. 13 labeled complaint cases + 3 known-miss drills seeded from the 2026-09-26 and 2026-10-03 audits; all cases correctly classifiable under v1.1 rules (legacy-tag thread sibin_91/2105505463530063992 recovered via the reply from the current handle).
